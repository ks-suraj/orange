  ### Step 2: Understand the system we need to build

  The system must have six distinct agent roles:

  1. **Orchestrator Agent:** Plans and coordinates investigations, manages
  shared state, delegates tasks, evaluates whether more evidence is needed, and
  decides when to stop.
  2. **Observability Agent:** Investigates logs, metrics, errors, and
  anomalies.
  3. **Dependency Agent:** Examines service dependencies, deployments,
  configuration changes, and possible cascading failures.
  4. **Reasoning Agent:** Develops and compares competing root-cause hypotheses
  using available evidence.
  5. **Critic Agent:** Challenges hypotheses, identifies missing or
  contradictory evidence, and requests targeted follow-up investigations.
  6. **Reporting Agent:** Produces a final incident report with ranked
  hypotheses, evidence, confidence, assumptions, and remediation
  recommendations.

  These must be meaningful agent roles with structured communication and
  genuine collaboration. Do not simply chain six LLM calls together and label
  each call an agent.

  Use a real LLM API for reasoning and evidence interpretation. A single
  affordable model may serve all six roles. Python should handle deterministic
  operations such as data retrieval, validation, tool execution, retry limits,
  and evaluation measurements. Do not hardcode answers for individual
  incidents.

  5. Architecture

  Shared state (InvestigationState) holds the incident, the task list with
  dependencies, an evidence ledger, hypotheses, critiques, budget counters and
  the reason the investigation stopped.

  Evidence and grounding:
  - Python creates an evidence ID for every tool result. Agents can't invent
    evidence; they can only cite IDs from the ledger.
  - A validator rejects any claim that cites a non-existent ID, so the
    evidence-grounding score is computed deterministically.

  Flow:
  1. Orchestrator (LLM) reads the incident and writes a plan: a list of tasks
     with dependencies.
  2. Observability and Dependency agents run in parallel threads. Each runs its
     own tool loop, capped at N tool calls, over its own tools:
     - Observability: logs and metrics.
     - Dependency: deployments, dependencies and historical incidents.
     - Each returns Findings: observed facts with evidence IDs, kept separate
       from interpretations.
  3. Reasoning builds competing hypotheses. Each has supporting and
     contradicting evidence IDs, a confidence and its assumptions.
  4. Critic either accepts, or returns specific challenges plus targeted
     follow-up tasks. Python sends those tasks back to step 2, for at most 2
     critique rounds.
  5. Orchestrator (LLM) decides whether to continue or stop. Python enforces
     hard stops: the round limit, the token and tool budget, a round with no new
     evidence, or the Critic accepting.
  6. Reporting writes the final report: facts, assumptions and inferences in
     separate sections, ranked hypotheses, remediation, and an explicit
     INCONCLUSIVE result when the top confidence is below a threshold or
     contradictions remain unresolved.

  Tool failures: each scenario's settings define faults: timeout, partial
  result, hard error, or fail-once-then-succeed. They're seeded so runs are
  reproducible. Python retries a bounded number of times, and only for
  recoverable faults.

  Baseline: a single agent with the same model, all five tools, the same
  tool-call and token limits and the same output schema, scored by the same
  grader.

  Metrics:
  - Accuracy: top-1 and top-3 match on the root-cause category and the service,
    plus whether "inconclusive" was correctly returned.
  - Evidence grounding.
  - Tool-call count, latency and actual tokens.

  Scoring is deterministic and uses no LLM judge, so it is cheap and repeatable.

  Scenarios (about 12): bad deploy, config change, database connection-pool
  exhaustion, upstream cascade, memory leak, certificate expiry, traffic spike,
  a misleading deploy (it coincides with the incident but the real cause is
  upstream), conflicting metrics, a log-tool timeout, partial metrics, and an
  insufficient-evidence case where the correct answer is inconclusive.

  1. Conclusion logic

  The decision is now made in code before the Reporting agent runs, and that
  agent is told the outcome and explains it. A report is conclusive only if all
  of these hold:
  - the top hypothesis has confidence of at least 0.5;
  - at least 2 verified supporting items that nobody disputes;
  - a lead of at least 0.05 over the runner-up;
  - contradicting evidence makes up no more than 35% of the evidence weighed.

  A critic objection counts only if it targets the top hypothesis, is marked
  material, and cites evidence that tools actually returned. Even then it only
  moves evidence between the support and contradiction counts; it can't force a
  result by itself. Critic approval doesn't bypass any of the criteria. The
  baseline uses the same function; it has no critic, so only its own
  contradicting evidence counts. Every value behind the decision is saved in the
  report.
